## Inline comments (5)

### 1. `backend/controllers/orderController.js`:127

**🔴 HIGH — Forged-payment bypass** _(security-mate · OWASP A01/A04)_

Ownership is now checked, but `isPaid` / `paymentResult` are set directly from `req.body` with **no server-side PayPal capture verification**. An authenticated owner (or admin) can mark their own order paid with fabricated payment data — the fix-1 doc explicitly defers the "verify capture server-side" half, so the bypass survives this PR.

**Fix:** capture/verify the PayPal order server-side (confirm id + amount + currency + `COMPLETED` status) before setting `isPaid = true`.

_Cross-mate: performance-mate confirmed the preceding ownership guard adds zero DB round-trips._

### 2. `backend/controllers/orderController.js`:103

**🟢 Correct fix + 🔵 LOW arch note** _(security-mate / architecture-mate)_

Record-level ownership check correctly closes the IDOR on `getOrderById`. ✔

**architecture-mate (LOW/C3):** this inline check is **NOT** an ADR-0003 violation — record-level ownership needs the loaded order and can't live in the coarse `admin` middleware. But the same logic is duplicated in `updateOrderToPaid` (L122) with a **divergent field access**: here `order.user._id` (populated doc) vs `order.user` (raw ObjectId) there. Both correct today, but copy-pasting either variant to a handler with the opposite populate state silently breaks authz.

**Suggestion:** extract a shared `assertOrderOwnerOrAdmin(order, user)` helper normalizing `order.user._id ?? order.user`.

### 3. `backend/controllers/orderController.js`:122

**🔵 LOW — Duplicated ownership check, fragile field shape** _(architecture-mate · C3)_

Same authorization branch as `getOrderById` (L103) but accesses `order.user` (raw ObjectId) here vs `order.user._id` (populated doc) there. Correct in both spots, but the divergence is copy-paste-fragile.

**performance-mate confirmed:** this guard adds **no DB round-trip** — `order.user` is already on the loaded doc; no `.populate()` triggered. The shape difference is intentional, not a perf smell.

**Suggestion:** one shared helper that normalizes both shapes.

### 4. `backend/middleware/authMiddleware.js`:15

**🟢 Correct fix + 🟡 MEDIUM follow-up** _(security-mate · OWASP A02 / architecture-mate)_

`algorithms: ['HS256']` correctly closes the algorithm-confusion / `none` vector at the centralized verify point. ✔ architecture-mate confirms this is ADR-0003-compliant (auth logic centralized).

**🟡 MEDIUM (security-mate):** algorithm pinning is moot if the secret is weak/unset. There is no `JWT_SECRET` strength check at boot — if it's undefined or the dev placeholder, tokens are trivially forgeable.
**Fix:** fail fast at startup if `JWT_SECRET` is missing or < 32 bytes.

_Related residual (MEDIUM, A06): `jsonwebtoken` is still `^8.5.1` (unmaintained); bump to `>=9` in an isolated commit. Both mates flagged this as security-owned._

### 5. `backend/routes/featureFlagRoutes.js`:9

**🟢 Correct fix + 🔵 LOW contract change + 🟡 perf note** _(3-way: security / architecture / performance)_

**security-mate:** admin auth now enforced server-side on both routes. ✔ **architecture-mate:** ADR-0003-compliant (admin enforced at the route boundary, not in the controller). ✔

**🔵 LOW breaking API contract (architecture-mate):** these routes flip public→admin-only (200→401). Existing anonymous frontend callers (`featureFlagActions.js`, `useFeatures.js` — two divergent fetchers, neither sends `Authorization`) will now 401. The documented frontend follow-up **must ship with this PR** or the admin screen breaks.

**🟡 MEDIUM perf (performance-mate):** `featureFlagController.readFeatures()` re-reads + `JSON.parse`s the 14KB `features.json` on **every** request to these now-live routes. Load once at module scope.
